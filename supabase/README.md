# إعداد Supabase لحسابات المدرسة

هذه ملفات إعداد جاهزة للمراجعة والتنفيذ في مشروع Supabase يملكه صاحب المنصة. لا تحتوي بيانات اعتماد أو كلمات مرور أو أسماء طلاب حقيقية. يوجد ملف تهيئة منفصل لبريد المدير الذي حدده صاحب المنصة. لم تُطبَّق على مشروع سحابي؛ يلزم صاحب المشروع تنفيذ الخطوات التالية وإجراء اختبار الدخول الفعلي.

## ما الذي يفرضه الخادم؟

- البريد وكلمة المرور وGoogle يعملان عبر **Supabase Auth الرسمي**. لا توجد قاعدة كلمات مرور داخل المنصة، ولا تُسجَّل كلمات المرور في جداول الإدارة أو سجلات الدخول.
- `allowed_accounts` قائمة بريد مطبَّع إلى أحرف صغيرة، والاسم المعتمد، وحالة التفعيل، وصلاحية المدير. لا يستطيع الطالب تعديلها.
- `student_profiles` يرتبط بمعرّف `auth.users`. البريد يأتي من سجل Auth نفسه والاسم من القائمة المسموحة، لا من حقل بريد أو دور يرسله المتصفح.
- كل طلب محمي يعيد التحقق من البريد المؤكد وقائمة التفعيل الحالية. تعطيل الطالب يمنع قراءة تقدمه أو حفظه حتى إن كان لديه رمز دخول سابق لم تنتهِ صلاحيته.
- `user_progress` يحفظ نسخة JSON خاصة بصاحبها. لا يستطيع الطالب قراءة نسخة طالب آخر، ولا يحصل المدير على تقدم الطلاب. التعديل متاح عبر دالة حفظ تفحص رقم الإصدار لمنع الكتابة فوق نسخة أحدث من جهاز أو تبويب آخر.
- `login_events` يسجل إنشاء جلسات Auth الحقيقية من محفّز خادم على `auth.sessions`. الوقت والبريد ومعرّف الطالب يحددها الخادم. تكرار استدعاء `record_login()` لا يصنع دخولًا جديدًا. لا تُحفظ كلمات مرور أو رموز جلسات أو عناوين IP في هذا الجدول.
- سجل النشاط يشمل جلسات الحسابات الموجودة التي لم تعد مسموحة، لكنه **لا يمثل محاولات كلمة مرور فاشلة أو تسجيلًا رفضه خطاف إنشاء المستخدم**؛ هذه لا تنشئ جلسة. الاسم وحالة السماح في الحدث يعكسان وقت تسجيله. الحساب المرتبط بأكثر من طريقة يظهر `unknown` حتى تصحيح الطريقة من مطالبات Auth الموقعة عند `record_login()`.
- الضيف وضع داخل التطبيق بذاكرة مؤقتة فقط. لا يُنشأ له مستخدم Supabase؛ دور `anon` ممنوع من الجداول والدوال المحمية. إغلاق الصفحة يفقد تقدم الضيف.

## 1. إنشاء المشروع وتطبيق الترحيل

1. أنشئ مشروع Supabase في حساب صاحب المنصة، واحفظ كلمة مرور قاعدة البيانات خارج المشروع.
2. افتح SQL Editor بصلاحية صاحب قاعدة البيانات وشغّل [001_school_auth.sql](migrations/001_school_auth.sql) كاملًا. يمكن إعادة تشغيل الإصدار نفسه دون حذف النتائج أو السجلات.
3. ينشئ الملف الجداول ودوال RPC وصلاحياتها وسياسات RLS ومحفّزات `auth.users` و`auth.sessions`. لا تغيّر ملكية دوال `SECURITY DEFINER` إلى دور طالب، ولا تعرض مخطط `school_private` في Data API.
4. لا تمنح `anon` أو `authenticated` صلاحية تعديل الجداول مباشرة. صلاحيات القراءة والدوال مضبوطة داخل الترحيل؛ لا تعطل RLS لتجاوز خطأ تكوين.
5. لا تجعل `auth` مخططًا معروضًا في Data API. إعدادات Supabase الافتراضية لا تعرضه.

الترحيل يستهدف Supabase الحالي الذي يحتوي `auth.users.is_anonymous` و`auth.sessions.not_after`. اختبار PostgreSQL المحلي يستخدم تعريفات مصغرة لهذين الجدولين؛ يلزم فحص التوافق في مشروع Supabase نفسه قبل الاستخدام مع الطلاب. إذا رفضت خدمة الاستضافة إنشاء محفّز على جدول Auth، لا تتجاهل الخطأ؛ راجع صلاحيات مشروعك، وسجّل النشاط من `record_login()` بعد التحقق من الجلسة مع توثيق فقد تسجيل الجلسات التي لم تفتح المنصة.

## 2. تهيئة أول مدير والقائمة المسموحة

للبريد الإداري المطلوب `ayobalbtoosh41@gmail.com` والاسم «أيوب محمد البطوش»، ينفّذ صاحب المشروع [bootstrap-owner.sql](bootstrap-owner.sql) بعد الترحيل. هذا الملف منفصل عن المخطط العام، ولا ينشئ كلمة مرور أو أي حساب طالب. أنشئ حساب Auth لهذا البريد من Dashboard، أو ادخل بـ Google بعد إعداد المزود والخطاف. لا توجد حاليًا قائمة بريد طلاب لتعبئتها تلقائيًا.

بعد تعديل البريد والاسم إلى بيانات صاحب المنصة، ينفّذ **صاحب المشروع فقط** SQL الآتي. لا تضع بريد المثال كما هو في بيئة الطلاب:

```sql
insert into public.allowed_accounts (email, display_name, is_admin, enabled)
values (lower(trim('owner@example.edu')), 'اسم مدير المنصة', true, true)
on conflict (email) do update
set display_name = excluded.display_name, is_admin = true, enabled = true, updated_at = now();
```

بعد ذلك أنشئ حساب هذا البريد من Dashboard → Authentication → Users، أو اسمح بدخوله بواسطة Google بعد تفعيل الخطاف أدناه. المدير داخل التطبيق يستطيع إضافة طالب أو تعطيله؛ لا يستطيع رفع طالب إلى مدير، ولا تعطيل آخر مدير مفعّل. ترقية مدير إضافي تتم من SQL Editor بواسطة صاحب المشروع، لا من بيانات عميل قابلة للتعديل.

لإعداد دفعة طلاب دون معالجة أي كلمات مرور، ضع ملفًا محليًا خاصًا بهذه الصيغة:

```json
[
  {"email": "student1@example.edu", "display_name": "اسم الطالب الأول"},
  {"email": "student2@example.edu", "display_name": "اسم الطالب الثاني"}
]
```

ثم شغّل:

```sh
node supabase/provision-allowlist.mjs students.json allowlist.sql
```

راجع ملف SQL ثم نفّذه في SQL Editor. البرنامج يرفض حقولًا إضافية مثل كلمة مرور أو صلاحية مدير، ويرفض البريد المكرر بعد التطبيع، ويكتب ملفًا جديدًا بصلاحيات محلية مقيدة عندما يدعم النظام ذلك. لا يطبع أسماء أو بريد الطلاب في سجل التشغيل. لا ترفع ملف الطلاب أو SQL الناتج إلى Git أو ملفات النشر. إضافتهم للقائمة وحدها لا تنشئ حساب Auth.

للحسابات ذات البريد وكلمة المرور المقدَّمة من المدرسة: أنشئ حسابات Auth من Dashboard → Authentication → Users → Add user، أو استخدم دعوات Supabase الرسمية ليحدد كل طالب كلمة مروره. إن أنشأت كلمة مرور مؤقتة، سلّمها عبر وسيلة خاصة ثم أرسل رابط إعادة تعيين Supabase الرسمي ليختار صاحب الحساب كلمة جديدة؛ لا تحتفظ بنسخة قابلة للقراءة في المنصة. ينطبق ذلك على حساب المدير أيضًا. لا تجعل كلمات المرور جزءًا من قائمة الطلاب أو سجلات الإدارة أو ملفات البناء. إنشاء المستخدمين آليًا، إن احتاجته المدرسة، يجب أن يعمل على خادم خاص بمفتاح خدمة؛ لا يوجد هذا المفتاح في تطبيق المتصفح.

## 3. منع التسجيل غير المسموح

1. في Authentication → Hooks، فعّل **Before User Created** كدالة PostgreSQL واختر `public.before_user_created`. إنشاء الدالة في SQL وحده **لا يفعّل الخطاف**.
2. فعّل تأكيد البريد في مزود Email. لا تسمح بالدخول ببريد غير مؤكد، ولا تستخدم `user_metadata.email_verified` بديلًا عن التأكيد الرسمي.
3. عطّل Anonymous Sign-ins؛ وضع الضيف المحلي لا يحتاجه.
4. لا توفر المنصة واجهة تسجيل حساب ذاتي. إن كانت جميع الحسابات منشأة مسبقًا من الإدارة، يمكن تعطيل **Allow new users to sign up** أيضًا. يتحقق الخادم من القائمة المسموحة لحسابات موجودة سلفًا في الحالتين.
5. إن أردت السماح لطالب مدرج بإنشاء هويته أول مرة عبر Google، فعّل **Allow new users to sign up** بعد تفعيل الخطاف. سيمنع الخطاف إنشاء غير المدرجين. تظل ملكية البريد خاضعة لتحقق Google أو تأكيد Email؛ لا تعطّل تأكيد البريد.
6. طبّق حدود المعدل وسياسة كلمات المرور وإرسال البريد في Supabase وفق عدد الطلاب. كلمات المرور الفاشلة وحالة SMTP تُفحص في سجلات Supabase Auth، ولا يزعم جدول نشاط المنصة تسجيلها.

RLS ودوال الوصول تظل مانعة للدخول غير المصرح حتى لو أُسيء تكوين التسجيل العام. لكن ذلك لا يغني عن الخطاف: بدونه قد تتراكم حسابات Auth غير مدرجة، وإن عجزت عن الوصول لبيانات المنصة.

## 4. إعداد GoogleOAuth

1. أنشئ Google OAuth Client من نوع Web application في مشروع Google Cloud يملكه صاحب المنصة.
2. أضف Authorized redirect URI المحدد في صفحة مزود Google في Supabase، عادة:
   `https://PROJECT_REF.supabase.co/auth/v1/callback`.
3. في Supabase → Authentication → Providers → Google، فعّل المزود وأدخل Client ID وClient Secret. السر يبقى هناك؛ لا يُنسخ إلى JavaScript أو Git.
4. استخدم النطاقات الأساسية `openid email profile` فقط. لا توجد حاجة لصلاحية Gmail أو جهات الاتصال.
5. في Authentication → URL Configuration، اضبط Site URL إلى رابط نشر المنصة عبر HTTPS. أضف عناوين العودة الفعلية بالضبط، مثل `https://school.example/` و`https://school.example/index.html` وعنوان localhost الخاص باختبارك. تجنب قائمة عودة عامة إلى نطاقات لا تملكها.
6. إذا كانت شاشة Google في وضع الاختبار، أضف حسابات الاختبار في Google Console أيضًا. تلك القائمة مستقلة عن قائمة المنصة؛ يجب اجتياز القائمتين عند الاختبار.
7. اختبر Google بحساب مدرج ومؤكد، وحساب غير مدرج، وحساب مدرج تم تعطيله بعد إصدار جلسة سابقة. إن ربط Supabase هويتَي Email وGoogle لبريد واحد، يبقى التقدم على معرّف Auth نفسه.

صفحة `file://` ليست عنوان نشر مناسبًا لدخول OAuth. استخدم نسخة HTTP المحلية أو HTTPS المنشورة.

## 5. إعداد المتصفح وعقد API

يضبط صاحب النشر **عنوان مشروع Supabase والمفتاح العام publishable أو anon فقط** في إعدادات الواجهة الموثقة في README الأساسي. هذه القيم ليست مفاتيح خدمة؛ الأمان يعتمد على Auth وRLS والتحقق في دوال الخادم. لا تنشر `service_role` أو secret key أو كلمة مرور قاعدة البيانات أو Google Client Secret.

يستخدم المتصفح عميل Supabase الرسمي، ولا يرسل كلمات المرور إلى جداول المنصة. بعد نجاح Auth يستدعي `record_login()` الذي يعيد نتيجة `platform_access()` أيضًا؛ إذا كانت `allowed=false` يرفض فتح حساب الطالب ويخرج من جلسة Auth. ويمكن استخدام `platform_access()` منفردة لإعادة فحص الصلاحية. لا تعتمد واجهة المتصفح وحدها لحماية البيانات.

| الدالة | المدخلات | النتيجة |
| --- | --- | --- |
| `platform_access()` | بلا مدخلات | `{allowed,is_admin,user_id,email,display_name,reason}` من هوية Auth الحالية |
| `record_login()` | بلا مدخلات | نفس النتيجة؛ يتحقق من جلسة Auth الموجودة، ويمنع تكرار حدثها |
| `platform_admin_roster()` | بلا مدخلات | `{accounts:[{email,display_name,is_admin,enabled,user_id,last_login_at,login_count}],login_events:[{id,user_id,email,display_name,at,provider,allowed}]}`؛ أحدث 500 حدث |
| `admin_allow_account(p_email,p_display_name)` | بريد واسم | يضيف/يعيد تفعيل طالب؛ لا ينشئ مستخدم Auth أو كلمة مرور ولا يمنح إدارة |
| `admin_disable_account(p_email,p_disabled)` | بريد و`true` للتعطيل أو `false` لإعادة التفعيل | حالة الحساب بعد التعديل |
| `save_user_progress(p_records,p_expected_revision,p_user_id)` | كائن JSON ورقم إصدار ومعرّف صاحب النسخة المتوقع | `{user_id,revision,updated_at}`؛ المعرّف والوقت من الخادم |

قراءة التقدم:

```js
const { data, error } = await supabase
  .from('user_progress')
  .select('records,revision,updated_at')
  .eq('user_id', session.user.id)
  .maybeSingle();
```

يجب تمرير `p_user_id` من هوية صاحب النسخة عند التقاطها للحفظ. يفحص الخادم تطابقه مع `auth.uid()` قبل أي كتابة؛ خطأ `progress_identity_mismatch` برمز `42501` يعني أن الجلسة تغيرت أو أن هوية النسخة لا تطابقها. أوقف المزامنة القديمة عندئذ؛ لا تغيّر المعرّف إلى حساب جديد مع الاحتفاظ بالنسخة القديمة. هذا المعرّف فحص للتطابق فقط: يظل هدف الكتابة مشتقًا حصريًا من `auth.uid()`، ولا يمنح اختيار حساب آخر. أُزيلت الدالة القديمة ذات المدخلين لمنع تجاوز الفحص.

عند عدم وجود صف يبدأ رقم الإصدار المتوقع من `0`. أول حفظ ينتج `1`. عند تحميل صف استخدم رقمه في الحفظ التالي، ثم خزّن الرقم الجديد من الاستجابة. خطأ `progress_revision_conflict` برمز SQLSTATE `40001` يعني وجود نسخة أحدث؛ **لا تعاود الكتابة بنفس البيانات دون إظهار التعارض واستعادة النسخة الأحدث أو دمجها**. إعادة ضبط تقدم الحساب تُحفظ ككائن `{}` عبر RPC بالإصدار الصحيح ومعرّف صاحبه المتوقع، لا بحذف صف مباشرة. شكل JSON المحتوى يخضع كذلك للتحقق في التطبيق عند الاستعادة؛ الخادم يفرض كائنًا لا يتجاوز 20 MB وعزل الملكية والإصدار.

## الاختبار والحدود

شُغّل اختبار PostgreSQL المحلي الموضح في [TEST_RESULTS.md](TEST_RESULTS.md). يستخدم PGlite الحقيقي مع جداول Auth ومطالبات JWT مصغرة لاختبار دلالات SQL وRLS والأدوار. لا يحاكي إصدار رموز Supabase أو التحقق من توقيعها أو تحويل Google أو إرسال البريد أو ربط الهويات. الاختبار السحابي الفعلي يحتاج مشروعًا مملوكًا وإعداد المزود وعناوين العودة وحسابات اختبار حقيقية.

لإعادة الاختبار دون إضافة اعتماد إنتاجي للموقع، ثبّت `@electric-sql/pglite@0.3.14` في مجلد مؤقت ثم مرّر المسار المطلق إلى `dist/index.js`:

```sh
npm install --prefix /tmp/school-sql-test --no-audit --no-fund @electric-sql/pglite@0.3.14
PGLITE_MODULE=/tmp/school-sql-test/node_modules/@electric-sql/pglite/dist/index.js node --test --test-isolation=none supabase/tests/security.test.mjs
```

هذه صيغة shell على Linux/macOS. على Windows PowerShell عيّن `$env:PGLITE_MODULE` إلى المسار المطلق للمكتبة في المجلد المؤقت، ثم شغّل أمر Node نفسه. يتطلب خيار الاختبار Node 22.8 أو أحدث؛ `--test-isolation=none` يُظهر الاختبارات الفرعية صراحة مع محرك WASM. لا يحتاج الموقع أو نسخته المستقلة هذه المكتبة في الإنتاج.

قبل فتح حسابات الطلاب الفعلية، تحقّق على مشروع تجريبي من: دخول Email وGoogle، رفض حساب غير مدرج، رفض بريد غير مؤكد، منع التسجيل بالخطاف، تعطيل جلسة قائمة، عزل تقدم طالبين، تعارض حفظ جهازين، ظهور السجلات بلا كلمات مرور، وعودة الضيف إلى حالة جديدة بعد إعادة تحميل الصفحة. لا يُعتبر إعداد الدخول منشورًا أو مجرَّبًا سحابيًا بمجرد وجود ملفات SQL.
