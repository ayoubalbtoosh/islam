# Supabase: التسجيل العام بالبريد وكلمة مرور المنصة

السياسة الحالية: أي طالب يستطيع إنشاء حساب ببريده وكلمة مرور جديدة خاصة بالمنصة. لا توجد موافقة بريد يدوية ولا تسجيل Google في الواجهة. كلمة مرور المنصة ليست كلمة مرور البريد. الضيف يبقى في ذاكرة التبويب، والمدير يرى بيانات الدراسة دون كلمات مرور أو رموز جلسات.

## ترقية المشروع الموجود

إذا طُبّق `001` أو الإعداد السابق، شغّل [003_public_email_signup.sql](migrations/003_public_email_signup.sql) وحده في SQL Editor. يعمل سواء طُبّق `002` أم لم يُطبّق، ولا يحذف المستخدمين أو التقدم أو سجل الدخول. لا تشغّل الترحيلات التاريخية لتحديث مشروع موجود.

**قبل أول تشغيل لـ003:** يجب أن يكون صاحب المشروع قد أنشأ حساب Auth المؤكد `ayobalbtoosh41@gmail.com` بنفسه، وتحقق من أنه حسابه الصحيح، قبل فتح التسجيل للطلاب أو تعطيل Confirm Email. الحساب الموجود في Supabase مستقل عن حسابك الذي تفتح به لوحة Supabase.

إذا غاب هذا الحساب أو لم يكن مؤكدًا، تفشل الترقية برسالة `owner_account_required` وتُلغى معاملتها بالكامل. أنشئه من Authentication → Users → Add user وأكّده لحسابك الذي تملكه، ثم أعد تشغيل003. لا ترسل كلمة المرور في المحادثة أو تحفظها في المشروع.

## مشروع جديد

1. أنشئ حساب Auth المذكور وأكّده أولًا من لوحة Supabase، قبل فتح التسجيل العام.
2. شغّل [setup-school.sql](setup-school.sql) كاملًا. يفحص وجود حساب المدير قبل أي تغييرات للسياسات، ثم يجمع المصادر الأصلية `001 + bootstrap-owner + 003` دون تعديلها.
3. يُربط المدير بمعرّف حسابه `auth.users.id` الثابت. الملف لا ينشئ مستخدم Auth أو كلمة مرور.
4. لا تُستخدم002 الخاصة بسياسة Google السابقة في الإعداد الحالي؛ تُحفظ كتاريخ للترقية فقط.

## إعداد Auth

- فعّل مزود **Email** و**Allow new users to sign up**.
- بعد نجاح ربط المدير، يمكن تعطيل **Confirm Email** للدخول الفوري للطلاب، أو إبقاؤه مفعّلًا لإرسال رابط التأكيد. الخادم يدعم الحالتين؛ Supabase هو الذي يقرر إصدار الجلسة. الحساب الذي لا يملك جلسة لا يقرأ البيانات المحمية.
- تعطيل Confirm Email لا يثبت ملكية البريد. حقل `email_confirmed_at` وحالة التأكيد المعروضان في الإدارة هما حالة سجل Supabase، وليسا ادعاء إجراء تحقق مستقل من صندوق البريد.
- عطّل Anonymous Sign-ins؛ الضيف المحلي لا يحتاج مستخدم Supabase. لا حاجة إلى Google Client ID أو Secret أو إعداد OAuth.
- خطاف **Before User Created** اختياري، ويمكن اختيار `public.before_user_created` من Authentication → Hooks. إذا كان مفعلًا سابقًا، فإن003 تحدّث الدالة نفسها لتقبل تسجيل Email الجديد وتمنع المعطل والمجهول. لا تعتمد على دالة001 أو002 القديمة وحدها.
- اضبط Site URL وعناوين العودة التي تملكها لتأكيد البريد أو استعادة كلمة المرور. كلمة المرور الجديدة تُدخل في واجهة المنصة وترسل مباشرة عبر عميل Supabase الرسمي؛ لا تُرسل إلى جداول الدراسة.

## صلاحيات المدير وحمايتها

- البريد الإداري المهيّأ هو `ayobalbtoosh41@gmail.com` والاسم «أيوب محمد البطوش».
- أول003 تربط حساب Auth الموجود المؤكد بمعرّفه الثابت في جدول خاص. تحقق الإدارة لاحقًا يتطلب هذا المعرّف نفسه والبريد الحالي المطابق وحالة التفعيل. حقول الأدوار في اسم الطالب أو JWT أو `allowed_accounts.is_admin` وحدها لا تمنح إدارة.
- حذف مستخدم المدير يحذف الربط، لكنه لا يحذف سجل تهيئته. إنشاء مستخدم جديد بالبريد نفسه، حتى لو كان مؤكدًا، ثم إعادة تشغيل003 لا يعيد الإدارة. يصبح الحساب الجديد طالبًا فقط.
- منع تعطيل آخر مدير يعتمد على الربط الحقيقي، لا على أي صف قديم يدعي `is_admin=true`.
- لا يرى المدير كلمات مرور الطلاب، أو تجزئات كلمات المرور، أو رموز Auth، أو بيانات اعتماد Supabase. لا يوجد RPC يعيد صفوف `auth.users` أو سجل التقدم الخام كاملًا.

إذا حُذف المدير وفُقد الربط، استعادة الإدارة عملية منفصلة لصاحب مشروع Supabase فقط: يراجع **معرّف Auth الجديد UUID** ويتحقق من ملكيته للحساب، ثم يربط ذلك المعرّف صراحة في `school_private.admin_bindings` بالبريد الإداري المعروف من SQL Editor. لا يُحذف سجل `admin_initialization` ولا تُستخدم إعادة التهيئة بالبريد كاختصار. لا توجد استعادة إدارة ذاتية من المتصفح، ولا يقوم003 باختيار معرّف بديل تلقائيًا.

## البيانات والحماية

- يُسجَّل Email الجديد تلقائيًا كطالب من هوية Auth الرسمية. الاسم للعرض فقط، يُنقَّى من محارف التحكم ويُحد إلى80 حرفًا. لا تمنح بيانات الاسم صلاحيات.
- الإضافة التلقائية تستخدم `ON CONFLICT DO NOTHING`؛ لا تعيد تفعيل حساب عطّله المدير ولا ترفع دور أي شخص.
- `user_progress` تظل قابلة للقراءة المباشرة لصاحبها فقط. حتى المدير لا يقرأ تقدم الآخرين بعملية SELECT مباشرة؛ دالة التفاصيل الإدارية وحدها تُعيد الحقول الدراسية المسموحة بعد فحص صلاحياته.
- حفظ التقدم يفحص هوية صاحب النسخة المتوقعة ورقم الإصدار؛ تغيير حساب SDK أثناء الحفظ أو الكتابة فوق إصدار أحدث يُرفض.
- سجل الدخول يأتي من جلسات Auth الحقيقية بوقت الخادم ومعرّفها؛ تكرار استدعاء التسجيل لا يضاعف الحدث. لا يُسجّل فشل كلمة المرور كدخول ناجح.
- يظل تعطيل الحساب نافذًا مع جلسة سابقة أو تحديث الاسم أو إعادة تشغيل الترقية.
- مخطط `school_private` لا يُعرض في Data API، والجداول الخاصة لا تُمنح للعميل. لا تعطل RLS ولا تمنح الكتابة المباشرة لتجاوز خطأ تكوين.

## عقد API

| الدالة | المدخلات | النتيجة |
| --- | --- | --- |
| `platform_access()` | بلا مدخلات | `{allowed,is_admin,user_id,email,display_name,reason}` |
| `record_login()` | بلا مدخلات | النتيجة نفسها، مع فحص جلسة Auth الحقيقية وتسجيل الحدث دون تكرار |
| `platform_admin_roster()` | بلا مدخلات | `{accounts,login_events}`؛ أدوار الإدارة مشتقة من الربط الثابت |
| `platform_admin_student_details(p_user_id)` | معرّف الطالب UUID | `{user,profile,progress,login_events,limits}` من الحقول الدراسية المسموحة |
| `admin_allow_account(p_email,p_display_name)` | بريد واسم | إضافة أو إعادة تفعيل اختيارية من المدير؛ لا حاجة إليها للتسجيل العام ولا تمنح إدارة |
| `admin_disable_account(p_email,p_disabled)` | بريد و`true/false` | تعطيل الحساب أو إعادة تفعيله |
| `save_user_progress(p_records,p_expected_revision,p_user_id)` | JSON ورقم الإصدار وهوية صاحب النسخة | `{user_id,revision,updated_at}`؛ هدف الحفظ من `auth.uid()` فقط |

دالة التفاصيل تشمل البريد والاسم وتاريخ إنشاء الحساب وحالة سجل تأكيد Auth، وملف الدراسة والنقاط والزيارات والنتائج والإجابات والأخطاء والجولة الجارية والإنجازات والإعدادات وسجل دخول الطالب. تُعاد النتائج المحفوظة كلها ضمن حد المخطط20000 نتيجة و20MB، دون حد100 القديم. تُستبعد مفاتيح JSON غير المعروفة وحقول كلمات المرور والرموز وبيانات اعتماد Auth. الإجابات تمر بالتحقق من أشكال خيارات الأسئلة الأصلية. بيانات الدراسة أبلغها تطبيق الطالب؛ لا تُعد درجات ممتحنة على خادم مستقل.

قراءة التقدم تتم من `user_progress` بمرشح `user_id=session.user.id`. عند غياب الصف يبدأ الإصدار المتوقع من0. خطأ `progress_revision_conflict` برمز40001 يتطلب جلب النسخة الأحدث أو دمجها، لا إعادة الكتابة العمياء. خطأ `progress_identity_mismatch` برمز42501 يعني أن الجلسة تغيرت؛ أوقف النسخة القديمة ولا تعيد تسميتها باسم مستخدم جديد. إعادة الضبط تحفظ `{}` بالهوية والإصدار الصحيحين.

المفتاح المسموح في المتصفح هو المفتاح العام publishable/anon وعنوان المشروع فقط؛ لا تنشر service_role أو كلمة مرور قاعدة البيانات أو مفاتيح الخدمة.

## الاختبارات والحدود

الاختبارات الحالية ونتائجها في [PUBLIC_EMAIL_TEST_RESULTS.md](PUBLIC_EMAIL_TEST_RESULTS.md). تستخدم PostgreSQL الحقيقي داخل PGlite مع جداول Auth ومطالبات JWT مصغرة؛ لا تختبر خدمة إصدار الرموز أو SMTP أو مشروع Supabase المستضاف.

```sh
npm install --prefix /tmp/school-sql-test --no-audit --no-fund @electric-sql/pglite@0.3.14
PGLITE_MODULE=/tmp/school-sql-test/node_modules/@electric-sql/pglite/dist/index.js node --test --test-isolation=none supabase/tests/public-email-signup.test.mjs
PGLITE_MODULE=/tmp/school-sql-test/node_modules/@electric-sql/pglite/dist/index.js node supabase/tests/setup-school.test.mjs
```

هذه صيغةLinux/macOS؛ فيPowerShell عيّن `$env:PGLITE_MODULE` إلى المسار المطلق ثم شغّلNode. Node22.8أو أحدث مطلوب لخيار الاختبار. لا تحتاج نسخة الإنتاج PGlite. اختبارات001 و002 محفوظة كتاريخ للسياسات السابقة، وليست وصفًا لسياسة التسجيل الحالية.
